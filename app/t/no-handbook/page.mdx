# There Is No Handbook

The most tempting way to use a coding agent is to stop thinking.

I understand the temptation. A good demo makes software feel frictionless: describe the feature, wait a few minutes, watch the diff appear. When it works, it feels like cheating. When it fails, it often fails in a way that exposes the part you skipped: the mental model.

That is the part I keep coming back to. Coding agents change the workflow, but they do not remove the need to understand the system. They make some kinds of work faster and some kinds of confusion more expensive.

There is no stable handbook for this yet. The tools are changing too quickly, the habits are too young, and the failure modes are still weird. The only durable advice I trust is boring: build enough understanding that you can work with the agent instead of being carried by it.

## The Overlap

Every serious technology shift has an overlap period where the old craft and the new machine coexist.

The printing press did not make scribes vanish overnight. Electric motors did not cause factories to rip out steam engines the next morning. For decades, people worked inside a mixed world: old skills, new tools, unclear economics, and a lot of premature certainty.

Software is in that kind of overlap now.

A year ago, most terminal-heavy coding workflows still looked familiar. Vim, Emacs, shells, scripts, build commands, local docs. Then Claude Code, Cursor, Codex, Windsurf, Ampcode, and similar tools pushed autonomous coding into the default conversation. Suddenly every serious developer workflow had a new question attached to it: what should the model do, and what should I still do myself?

Committing completely to one answer feels premature. The toolchain changes every few months. The best practices are not settled. The only certainty is that the interface between engineer and codebase is being renegotiated in public.

## Friction Still Teaches

Software engineering is not just the act of producing code. It is the practice of building useful mental models under uncertainty.

That is why friction matters. Chasing a bug through a large codebase teaches you where the boundaries are. Reading an unfamiliar subsystem teaches you which abstractions are real and which ones are politeness. Writing a feature by hand teaches you which parts of the design fight back.

Agents can accelerate that work. They can also let you skip the part that makes you better.

Mitchell Hashimoto's post on [vibing a non-trivial Ghostty feature](https://mitchellh.com/writing/non-trivial-vibing) captures the useful version of this. A strong mental model made the agent more effective, not less necessary. The human still knew where to look, what mattered, and how to judge the result.

That is the difference between using an agent and outsourcing your judgment.

## Quantum Bugs

![Quantum Bugs](/t/no-handbook/quantum.jpg)

Some bugs only become visible after you have stared at the system long enough.

I think of them as `quantum` bugs: runtime problems that appear only under specific timing, platform, state, or integration conditions. They are not obvious from the code in front of you. They live in the boundary between code and reality.

An Objective-C to Rust FFI boundary leaks memory only on one macOS version. A port killer checks that a process is running, another task starts a replacement, and the delayed kill lands on the new process. A feature works in Monterey and panics in Sonoma because a platform API changed under a wrapper that looked stable.

These bugs punish shallow understanding. You cannot fix them by asking for "a better implementation" over and over. You need hypotheses. You need reproduction. You need to know which state is trustworthy. You need enough confidence to keep digging after the first three explanations fail.

Current agents still struggle here. They often try a few patches, fail to move the symptom, and then reach for a rewrite. Sometimes that is useful. Often it just resets the evidence.

The engineer's job is to keep the investigation coherent.

## The Memory Problem

Agents also have a strange relationship with time.

They can read a huge amount of context inside a session, but they do not naturally develop the memory of someone who has lived with a system. They reboot. They lose the morning. They miss that you edited the file ten minutes ago unless you make them reread it. They treat stale docs as confidently as fresh source code unless the workflow forces source to win.

I have added timestamp hooks to coding-agent sessions just to make relative time less ambiguous. Without that anchor, "this morning" and "yesterday's bug" are vague prompts. The model may search for the wrong era of documentation or reason from a snapshot that is no longer true.

The same problem shows up in repo instructions. `CLAUDE.md`, `AGENTS.md`, carefully tuned prompts, local scripts, and memory files are all attempts to patch a missing continuity layer. They are useful, but they are also awkward. It can feel like writing `INTERN_1.md` for every new teammate who joins the project for an afternoon.

Maybe continuous learning, specialized model state, or better project memory changes that. Until then, engineers have to treat the codebase as the source of truth and make agents re-enter the current world often.

## What I Trust Right Now

I trust workflows that preserve human judgment.

That means agents can write drafts, inspect unfamiliar code, run experiments, generate tests, and propose changes. It also means I want the human to understand the shape of the system, review the diff, read the failing logs, and know what evidence would change their mind.

The right amount of friction is not fixed. For a throwaway script, I am happy to let the model run. For a production migration, I want smaller steps, better rollback, and proof at every boundary. For a hard debugging session, I want the agent gathering evidence while I keep the investigation pointed at the real failure.

That is not a grand philosophy. It is a working posture.

## Testing The Waters

We are early enough that confidence should feel suspicious.

The tools will change. The interface will change. The rituals around prompt files, agent memory, MCPs, sandboxes, and review will look dated faster than most of us expect. A workflow that feels obvious in 2026 may feel quaint in 2027.

So I am trying to stay flexible without becoming passive. Build the mental model. Use the agent. Keep the parts of engineering that make judgment better. Let the tools remove drudgery, not responsibility.

There is no handbook yet. That is the unsettling part, and also the fun part: the only honest way through is to keep working, keep measuring, and write down what survives contact with the code.
