# We only need MCPs because we don't trust LLMs

If a new engineer joined your team and needed to work on GitHub, you would not give them a tiny GitHub-shaped toy interface. You would install Git, install the GitHub CLI, grant the right permissions, and expect them to learn the real tools.

We treat language models differently because we do not trust them yet.

That is the hidden premise behind most MCP servers. They are not mainly breakthroughs in interface design. They are trust boundaries. They exist because the model behind the keyboard is not trusted with the same broad environment a human engineer would get.

That was the right tradeoff for a while. Models got stuck in loops, called the wrong tools, lost track of state, and confidently damaged things they did not understand. A narrow tool surface made sense when the operator was unreliable.

But the capability curve moved. Around the Opus 4.5 moment, people who would never have allowed a model to run code locally started launching multiple coding agents with fewer restrictions. The default posture shifted from "approve every move" to "let it work in a sandbox and inspect the result." Once that shift happens, the old MCP philosophy starts to look less like safety and more like friction.

## The safety layer belongs in the environment

Tool-level control is not how we usually secure powerful systems.

We do not protect a company by inventing one API for every acceptable human behavior. We use authorization, scoped credentials, audit trails, network boundaries, disposable environments, and rollback. We decide what a person or service can reach. We do not try to predefine every verb they are allowed to think with.

Agents should follow the same model.

Bash is the clearest example. People talk about shell access as if the shell itself is the dangerous part. It is not. Unbounded access is dangerous. Give a model shell access on your laptop, with your home directory, private keys, production credentials, and unrestricted network, and you deserve the blast radius you created.

Give that same model shell access inside a disposable sandbox, with a small mounted workspace, no sensitive credentials, controlled network access, logging, and rollback, and the shape changes. The model gets a general tool. The system keeps the boundary.

That is a better design than dozens of tiny pseudo-tools pretending not to be a shell.

## MCPs still solve a real problem

MCPs are useful because they make tools easy to share.

A few lines of config can give a model access to a service another developer wrapped. Remote MCPs can avoid downloading arbitrary code into the agent harness. A well-designed MCP can expose a narrow, stable, authenticated surface around a product API.

That is real value. It is just not the same thing as the future of agent interfaces.

The weakness is context and rigidity. Many MCPs hand the model a large set of tools, each with a schema the model has to carry around. Some servers expose thirty verbs where four commands would do. Others wrap a CLI that was already a better interface. The model pays for the abstraction every turn.

The protocol can improve. Progressive disclosure helps. Better tool loading helps. But that only addresses part of the issue. The deeper question is whether a model should be trapped behind tiny verbs at all.

## Smaller tools are not the end state

The durable pattern is not "give the model less interface." The durable pattern is "give the model a real environment with real boundaries."

Products like [OpenClaw](https://github.com/openclaw/openclaw) arrived at the right time because they match what users are learning from stronger models: they want fewer handrails in the tool layer and stronger guarantees in the execution layer. They want a system that can explore, write code, run commands, inspect output, and recover from mistakes.

That does not mean every model should get every tool. It means the boundary should be explicit. A model should know what files it can touch, what network it can reach, what credentials exist, how work is logged, and how changes are reverted. The safety model should survive even when the model uses a general tool creatively.

## The bridge technology

Most MCPs will not disappear overnight. They solve distribution, auth, and integration problems that are still awkward. They are especially useful for services that do not have good CLIs or where the API surface needs a product-owned contract.

But as a safety philosophy, MCPs are bridge technology.

They belong to the era when models were too brittle to trust with a normal computing environment. As models get more competent, the interesting work moves down a layer: sandboxing, checkpointing, scoped credentials, auditability, and agent auth.

The future is not smaller tools. It is better rooms to let the model work in.
